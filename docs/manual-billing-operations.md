# Operator guide: confirm a manual subscription payment

This queue is for the **platform operator**. It is not the store owner's queue for customer orders. No action here contacts a bank, charges a card or sends a refund. A signature adapter exists for contract tests; there is no public checkout provider or webhook to configure.

## Before taking payments

1. Back up the platform DB and tenant volumes together. Run **one writable platform process**. For a first rollout, stop the old managed workers in a maintenance window. Inventory existing plans and any independently documented paid ends. Set `PLATFORM_ENABLED=1`, `PLATFORM_BILLING=1`, a dedicated strong `PLATFORM_OPERATOR_TOKEN`, an HTTPS `PLATFORM_PUBLIC_URL`, and private writable data volumes. Do not put these credentials in worker `.env` files. Customer reports are independently optional.
2. Start the platform. Open `/platform/operator/billing` over HTTPS and use the operator sign-in form. Set a monitored `PLATFORM_OPERATOR_EMAIL` (or `PLATFORM_BILLING_OPERATOR_EMAIL`) and mail adapter **before login**. A successful login requires alert acceptance; file mail is for development only. No customer session, including a customer account with role `admin`, is an operator login. A legacy remaining trial keeps its end; an unverified legacy plan label **does not become a paid term**. A legacy tenant with no remaining trial starts paused. Record a reasoned comp/extension if an existing agreement warrants it. This is not reported as cash. Resume/go live using the normal readiness checks; don't pair the number again just to change a plan.
3. In **Publish a plan version**, copy the free specification. For a paid plan set a new `plan` key, display name, positive `rank`, currency, feature allowlist, limits, and an `offers` map. Its keys are calendar-month counts; its values are **integer minor units**, not major-unit decimals. Offer 1, 2 and/or 6 months if those are the durations you sell. There are **no default customer prices**. Publish another version to edit; setting `offered: false` withdraws it from new checkout. Existing purchased terms keep their version. To change future trials, publish a new `free` version with `trialDays` and explicit limits.
4. In **Payment instructions and policy**, set only the transfer methods you actually accept. Each has a method label, receiver name and/or payable alias, and optionally the **last four** account digits. Do not enter a full account number, card details or credentials. Instructions and tax are snapshotted on the invoice. Configure optional `taxLabel` and integer `taxBps` (0 disables); tax is rounded half-up once on the subtotal. This is a calculation, **not tax advice**.
5. Replace both customer policy placeholders: **Terms** — `[operator: add approved term, cancellation, export and deletion terms]`; **Refunds** — `[operator: add eligibility, timeframes and a private contact channel]`. Set grace, retention, final wait, proof life, operator review SLA and worker cache lifetime deliberately. Decide whether to opt into anonymous accounting aggregates after deletion. Obtain advice for your jurisdiction; no legal retention period or refund entitlement is asserted here.
6. Configure a production mail adapter supporting PDF attachments and idempotency keys. `PLATFORM_MAILER=file` writes private local files; it does not send mail. Optionally set `PLATFORM_BILLING_OPERATOR_EMAIL` for review-overdue email; otherwise use the queue. Run `npm run doctor -- platform`. Use a disposable tenant and synthetic proof to rehearse, including export and reversal. Do not run a second control-plane writer against the live database as a cron job.

### Operator access

Use a random operator credential independent of customer, platform and tenant secrets. Both operator surfaces reject standing Basic credentials. Set `PLATFORM_OPERATOR_TOTP_SECRET` to an independent Base32 seed (at least 20 random bytes, no padding) and provision the same seed privately in the operator's authenticator: SHA-1, 6 digits, 30 seconds. Keep clocks synchronised and protect a recovery copy separately. An invalid configured seed fails closed; successful codes cannot be replayed. To recover, restrict network access to the operator console, replace the operator credential and authenticator seed, restart the platform, test the alert and login, then reopen access. Do not send seeds by email.

Sessions expire after 15 minutes even with activity; reload and sign in again. Restart or credential rotation invalidates sessions. Login is limited per IP and across the installation; five failures in 15 minutes lock the operator identity for 15 minutes, including across restarts. Inspect `operator_login`, `operator_login_failed` and `operator_locked` in the platform audit. A provider accepting the login alert is not proof it reached the mailbox. Use a dedicated account/mailbox and monitor bounces. Do not share customer passwords with operators.

## Review a transfer

1. The owner selects an offer in **Plans and billing**. For a higher tier during a paid term, the operator enters the **difference in minor units** in the quote card; only then is an unpaid invoice issued. A quote isn't a receipt or a request to transfer an unspecified amount. For a lower tier the owner schedules the change for the end and can prepay the next term.
2. Read the invoice number, unique `PAY-…` reference, currency, balance and selected tenant. Open **Read masked proof**. Its fields identify the source: submitted text, first-page PDF text, optional local image OCR, or an owner's transcription. A missing field means *unknown*, not “passed.” The stored copy is not a bank statement or an image archive.
3. **Independently match the actual credit in the receiving account.** Check the currency, amount, receiver, date, payment reference and whether this credit has already been booked. A matching screenshot, hash, reference fragment or risk label is never sufficient. Do not request a PIN, card number or security code. Do not paste bank transactions in audit reasons.
4. Choose one action:
   - **Confirm received money:** type the amount actually received in the displayed currency's minor units. Full settlement grants the term (or upgrade difference); partial settlement issues a receipt but leaves the balance open and grants no term. Excess or mismatched currency is refused. A retry of the same confirmation uses the same payment and receipt.
   - **Request more information / Reject with next step:** select a neutral reason. The owner sees the corresponding explanation and can provide new redacted evidence. **Recheck** refreshes deterministic checks; it never decides a payment. A proof over the configured SLA is visible as overdue.
   - **Reverse confirmation:** use only for a mistaken credit/confirmation, select the reason and write a short explanation (also required for manual extensions). Do not include payment details or personal data. The original payment and number stay recorded, the invoice reopens, and the entitlement is recomputed from the remaining grants. A reversed receipt is identified as such on download. **Record refund only** records an amount/reason; arrange and verify any real refund separately. A refund record alone does not reverse a grant.
5. The owner can download the numbered receipt. Its email is a separate outbox intent, retried after 10, 20, 40 minutes and so on (24-hour cap), with the same idempotency key. If a mail adapter or host fails, restore it and retry delivery; **do not accept the payment again to resend mail**. Check the queue, confirmed-by-currency revenue, cancellation counts and billing audit. The operator view contains no tenant chat transcripts.

## Running and stopping

- Times in storage and month arithmetic are UTC. Defaults: 7/3/1-day renewal reminders, 3-day paid grace (never trial grace), 30-day canceled retention, export reminders at day 0/15/25, then 7 days in pending deletion before timeout. Maintenance picks the current reminder window after downtime; it does not send every obsolete reminder at once. Renewal reminders stop on cancellation. Terms/retention dates are visible to the owner.
- The billing lease is refreshed each minute and on term changes. A linked billing-aware worker can soft-pause/resume without logging out. If the platform stops refreshing, the old lease is good only until the earliest of its term/version boundary or cache deadline (12 hours by default). A missing/unreadable lease fails closed. Never treat this process/filesystem boundary as protection against a hostile host administrator. A worker that was stopped or lost its key needs normal go-live; an owner pause is not automatically undone.
- The default paused response is silence. An owner can allow one fixed handover message per contact per day where transport/consent permits. Monthly worker caps count distinct admitted contacts, inbound video attempts, and reserved voice seconds (decoded sample time for STT; maximum bounded clip for TTS attempts). These aren't provider-billed minutes. Limit alerts are deduplicated. Report range and history retention are separate from subscription retention.
- An expired trial or ordinary non-renewal **does not** start data deletion. An explicit cancellation does. A primary owner in `pending_deletion` can export account data, then confirm the exact assistant slug for early permanent deletion. Timeout uses the same tenant-specific stop-and-forget path, never deletes sibling assistants, and does not scrub the whole account. Maintain a separate access/expiry policy for backups and externally delivered mail.
- To disable this feature on a previously enrolled fleet, stop managed workers first; reconcile open invoices and pending deletion dates, then disable the flag and restart the platform/workers deliberately. Disabling billing switches back to legacy plan enforcement; it is not a cancellation or a refund. Offline platforms cannot deliver or purge until running again.
